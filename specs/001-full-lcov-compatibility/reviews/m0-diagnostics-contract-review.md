# M0 Diagnostics Contract Review

## Decision

The standalone LCOV 2.5 diagnostics, error-control, and command-exit inventory
is acceptable as an M0 contract. It is a pinned-source and retained-Oracle
reference contract only. It does not make any of the 71 planned diagnostic or
parallel cases executable, authorize M1 implementation, or provide Ferricov
product compatibility evidence.

## Classification

- Review class: `Critical`
- Reason: diagnostic categories, continuation controls, stream ownership, and
  command exit folding define user-visible failure semantics across every
  installed command and future parallel execution.
- Product code changed: no
- Persisted or public data contract changed: no; this standalone inventory does
  not change the public inventory schema, Suite schema, output formats, or save
  semantics.

## Semantic Oracle

The review uses these verifiable invariants:

1. The shared registry contains exactly 32 ordered, case-insensitive category
   names with their pinned numeric identities.
2. The category scan retains exactly 399 symbol references under `bin/`,
   `lib/`, and `scripts/`, bound by per-category counts and hashes.
3. `branch` remains accepted by the shared registry but is classified as
   `reserved_no_production_emitter`; no other category receives that status.
4. Exactly nine reviewed rules retain ignore-list precedence, repeated-name
   counts, keep-going, fatal/warning/silent ladders, suppression accounting,
   and final error-summary folding.
5. Parser errors, raw Perl failures, native Python diagnostics, and early
   dependency failures remain distinct unclassified surfaces rather than being
   coerced into named categories.
6. All ten installed commands retain an explicit exit policy, including the
   `xml2lcovutil.py` library-only boundary.
7. All 71 `DIAG-*` and `PAR-*` identities in the normative specification remain
   ordered and `planned`; none has product evidence.
8. All 52 retained Oracle observations preserve exact case identity, exit,
   stdout, stderr, output, and observation hashes as applicable.
9. The retained `m0-core-geninfo-startup-control` observation remains a
   `startup_environment_intercept` with exit `30` and no planned-case binding.
   It cannot satisfy the writable-temporary-directory
   `DIAG-NOARGS-GENINFO-001` oracle, whose normative exit remains `255`.
10. Root and entry-level product evidence remains empty or false, while all
    retained observations remain `oracle_reference` only.

## Reverse Review

The mutation suite proves rejection of:

- a missing category;
- a category-order swap;
- a category symbol-reference closure change;
- promotion of reserved `branch` to an emitted category;
- changed control-rule source text;
- a command exit-policy change;
- a missing planned case identity;
- same-count Oracle stderr identity swaps;
- retained artifact hash drift;
- mapping the intercepted `geninfo` startup observation to the true no-argument
  case;
- product-evidence injection; and
- promotion of an Oracle reference to product status.

The generator also hard-binds all three retained aggregate artifacts, the
pinned upstream commit, exact registry order, source text, planned-case order,
and committed generated bytes. Assuming a compatibility regression had
occurred, these checks would reject source, evidence, or status drift before a
reviewer could mistake a regenerated inventory for passing product behavior.

## Residual Risk

The 51 observations are retained references, not an executable acceptance
suite for all 71 planned identities. They cover no ignore-two transition,
warning promotion, suppression threshold, converter keep-going trap, parallel
worker lifecycle, or writable-temporary-directory `geninfo` no-argument case.
Future work must add exact Oracle and Ferricov executions for those identities
without weakening the distinction between reference evidence and product
evidence.
